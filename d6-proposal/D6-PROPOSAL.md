## 1. Purpose

Generation was never wired into the v2 production worker — by design, not by omission. The production worker `opalreader-api-v2-prod` ships with no queue binding, no queue handler, and no provider secrets, so there is no switch to flip: setting `GENERATION_HALT` to "0" alone would change nothing observable (grants would have no delivery path; synthesis would fail at `provider_not_configured`) (preflight, "Bottom line"). D6 is therefore a **build project**: add the missing plumbing to the production worker and the accepted client, lift the two production-activation blockers (§4, §5), and arm the result through a separately-gated sequence. The end state: Julie can generate the missing Forever Pucked segments — 357 of its 407 segments have no audio yet (census) — and later the other books' unbound segments, from the accepted UI, on the Standard lane, truly hands-off (Julie's feature law, confirmed Oct 20): she submits one intent and the coordinator owns continuation server-side (§6.5) — the work proceeds across quota rollovers and app closures without her, until it is done or a stop condition reports itself. The safeguards in this proposal hold at every step.

## 4. Blocker A — D10 flush-before-commit (design)

Rowan's requirement (`v2/p8/part1-decisions.md`, via preflight): the executor must flush *and verify* durable audio bytes in R2 before any binding/report commit, with failure-injection tests. The current executor is not accepted as production durability today. The build redesigns the executor's commit order as follows:

**Commit order (per occurrence):**
1. Synthesize via the provider adapter (Standard lane; §6.4).
2. **Flush**: write the audio object to R2 under its binding cache key.
3. **Verify**: re-read the object's durable state from R2 and confirm (a) the object exists at the expected key, (b) its byte size equals the synthesis result's byte size, and (c) its ETag matches the flush response's ETag. All three must hold; a HEAD/metadata read is sufficient — the design does not re-download the audio body. (Whether the R2 binding's head response exposes both values in the deployed runtime is TO BE PINNED IN BUILD; the invariant — existence + size + ETag equality — is what is specified here.)
4. **Only then commit**: write the binding row and the job/report record, and settle the ledger, as one coordinator-side step. No binding, report, or "ready" state may exist for an occurrence whose step 3 has not passed in this execution or a verified prior one (see FI-4).

**Commit atomicity, the execution record, and honest attempt accounting (Amendment A-1 — Rowan clarification 1, Q5).** The step-4 commit is specified as **one Durable Object SQLite transaction** in the coordinator covering exactly three writes: the binding row, the job/report record, and the ledger settlement. It is **idempotent on (occurrenceId, executionId)**: re-executing the commit for the same pair is a no-op, so a retry of the commit step itself can never double-bind, double-report, or double-settle. Around that transaction, accounting uses Rowan's four-way vocabulary throughout this proposal:

- **Reserved grants** — quota/cap reservations the coordinator has granted but not yet dispatched. A reservation is not spend.
- **Attempted calls** — provider calls actually made. Every attempted call is recorded in a separate **append-only attempt log written at attempt time — before synthesis** — so the record of the attempt survives any later failure, including failures that never reach the commit transaction. A failed flush or verify never erases the attempt record; the quota counts *attempts* (preflight: `/v2/quota` exposes attempts today / spent).
- **Actual known cost** — the settled cost of an attempted call whose billing outcome is known. Only known cost counts against the phase budget (§9).
- **Unknown billing outcomes** — attempted calls whose billing cannot be determined. An unknown outcome is never treated as free and never blindly retried: it moves the occurrence (and, per §9, the phase) to reconciliation first.

**Durable discoverability and crash recovery.** Before synthesis, the executor writes a durable **per-occurrence execution record** in the coordinator carrying a state machine — `granted → attempted → synthesized → flushed → verified → committed`, plus `failed` and `unknown-billing` states — keyed by (occurrenceId, executionId). Because the record and the R2 key are both durable before the work they describe, a verified R2 object is **durably discoverable after a crash**: on recovery, a scan enumerates all non-terminal execution records and resumes each from its recorded state — a `flushed` or `verified` record is re-verified against R2 (existence + size + ETag, §4 step 3) and committed **without re-synthesis** (this is the general recovery path of which FI-4 is the test case); a `synthesized` record re-enters at flush; an `attempted` record whose billing outcome is unknown goes to reconciliation (§9), never to blind retry. No path synthesizes an occurrence twice for the same execution, and no new execution (new grant) is created for an occurrence with a non-terminal record until that record reaches a terminal state.

**Failure semantics:**
- Any failure at steps 2–3 → **no commit of any kind** for that occurrence: no binding row, no report entry, the occurrence remains unbound and eligible. (The attempt-log entry stands — see above; "no report entry" means no job/report claim of a result, not erasure of the accounting.)
- The occurrence returns to pending/eligible. It is retried only under the server-owned repair-chain rules (§6.4) with a bounded attempt count (the exact bound is TO BE PINNED IN BUILD), never in a hot loop within a single execution — and only after any unknown billing outcome on its prior attempts has been reconciled.
- A flushed-but-unverifiable object is treated as an orphan: preserved in place, flagged in the job report by key, never silently deleted — consistent with the migration's standing preservation dispositions.
- A failure is surfaced in the job's report with its stage (flush / verify / commit) named, so a stuck book reports *where* it stopped, in the same spirit as the client's truthful sync states.

**Failure-injection tests (build battery, §7):**
- **FI-1** — kill after synthesis, before flush: no R2 object, no commit, attempt recorded once.
- **FI-2** — kill after flush, before verify: object present, no commit; recovery path re-verifies or orphan-flags — and never re-synthesizes without a new grant.
- **FI-3** — verify returns a mismatch (size or ETag differs): no commit, failure surfaced with stage = verify.
- **FI-4** — kill after verify, before commit: on recovery, the executor re-verifies the already-flushed object and commits **without re-synthesizing** (commit is idempotent against a verified flushed object; no double spend).
- **FI-5** — R2 write error mid-flush: no commit, no partial object treated as valid, attempt recorded.
- **FI-6** — crash-recovery scan: kill the executor at each execution-record state in turn (`attempted`, `synthesized`, `flushed`, `verified`); on recovery, the scan resumes each record from its state with zero re-synthesis for `flushed`/`verified` records, exactly one idempotent commit per (occurrenceId, executionId), and an `unknown-billing` record routed to reconciliation with zero retries attempted.

## 6. Build scope (repo-only, gated)

### 6.1 Queue topology — decision required

The shared-queue question, head-on: the account's only queue, `opalreader-generation`, has the frozen v1 worker as its only consumer. **Unpausing it is not an option** — it would feed frozen v1, not v2 (preflight). Options:

- **Option 1 (recommended): a new v2-dedicated queue** (name TO BE PINNED IN BUILD, e.g. an `opalreader-generation-v2` form), produced by the v2 worker's outbox drain and consumed by the v2 worker itself. v1's queue, consumer, and paused delivery are never touched; the frozen rollback keeps its exact shape; each worker's traffic is independently pausable; arming and re-halting (§8) act on v2's queue only.
- **Option 2: share `opalreader-generation` with a second (v2) consumer.** Rejected: queue messages are delivered to consumers without lane/version routing guarantees this design can rely on; v1 could receive v2 dispatches while frozen (its mutating routes return 423, but relying on a frozen worker to refuse misdelivered work is not a design), and unpausing delivery for v2 would simultaneously resume delivery toward v1. The failure modes are exactly the ones the freeze exists to prevent.
- **Option 3: no queue — synchronous execution inside the command request.** Rejected: generation is long-running and hands-off by design (feature law); the accepted trigger path is queue-based (preflight), and synchronous execution would break quota-ordered granting and the repair-chain model.

Recommendation: **Option 1**. Rowan approved the dedicated v2 queue (comment 6500137494, Q1): v1's paused queue is never resumed or shared. **TO BE PINNED IN BUILD, before deployment:** the new queue's exact name and ID, its free-tier operations allowance and per-operation cost (expected zero on the free tier — verified, not assumed), and its consumer routing (producer = the v2 worker's outbox drain; consumer = the v2 worker itself).

### 6.2 Worker production entry

Per the preflight's recommended build shape: a production entry variant of the v2 worker adding the queue producer (outbox drain → the new queue), the queue consumer handler (consumer → `/internal/execute`, the source-verified path), and provider-secret support (the code reads `GEMINI_API_KEY` from the worker's own env; the build references the secret **by name only** — setting it is Julie's step, §6.3). The frozen Shelf bridge is untouched (byte-identical, hash-pinned as in every prior round). Playback, sync, and diagnostics behaviour is unchanged; the existing batteries must stay green against the new entry.

### 6.3 Provider secret — Julie's hands only

The build never touches the secret value. Setting `GEMINI_API_KEY` on `opalreader-api-v2-prod` is a **Julie-hands-on step** (the D2 token pattern), sequenced as gate step 3 (§8). The deploy (step 4) is verified with the secret present-by-name only; no agent reads, prints, or transmits the value at any point. Secret **existence** is verified by binding-name presence only (Amendment A-1 — Rowan clarification 6); Rowan's design review authorizes no secret-setting, deploy, arming, smoke, or production spend — each remains Julie's separate gate (§8).

### 6.4 Executor: repair chains, POLICY_BLOCK splitting, voice law

- **Server-owned repair chains for all generation** (feature law, confirmed Oct 20): retry/repair decisions live in the executor, not the client. The client submits intent; the chain owns attempts, splits, and terminal states.
- **Recursive POLICY_BLOCK splitting without voice substitution** (feature law): when the provider refuses a segment with POLICY_BLOCK, the executor splits the segment text and retries the parts recursively, keeping the same cast voice throughout — never substituting a different voice to get past a block. The **original text is preserved across every split** (parts concatenate to the segment's text exactly; nothing is rewritten, trimmed, or re-worded to slip past the filter). This path is load-bearing, not edge-case: all 18 unbound Forever Pucked Ch 2 segments carry a v1 POLICY_BLOCK failure record (census), and several bound segments elsewhere in the book succeeded in v1 only after splits. A segment that still fails at the recursion floor reaches a terminal blocked state, is reported by ID in the job report, and does not halt the rest of the job — it is never skipped silently and never voice-substituted.
- **Finite split floor and per-segment attempt budget (Amendment A-1 — Rowan clarification 5).** The recursion and the repair chain are bounded. Proposed ceilings, for Rowan's ruling — the exact values are TO BE PINNED IN BUILD **within** these ceilings: **recursion depth ≤ 4** (a segment splits into at most 16 leaf parts); **minimum part floor 50 characters** (no split may produce a part shorter than 50 characters; a refusal of a part that cannot be split further without breaching the floor is terminal for that part); **per-segment attempt budget ≤ 12 attempted calls** across the segment's entire split tree and repair chain combined (every part attempt and retry counts; exhausting the budget is a terminal blocked state, reported by ID). The ceilings are set well above the split behaviour v1 actually needed, while keeping the worst case per segment bounded in both quota (12 of 100 daily attempts) and cost (bounded again by the §9 phase budget's fail-closed stop).
- **Removed-provider voices — prompt, never silent substitution** (feature law): when a segment's cast voice belongs to a removed provider (Azure / Fish / Speechify / ElevenLabs), generation for that segment stops at a **voice-mapping prompt** naming the character and the recorded mapping where one exists (recorded only: Emmett → Gemini Charon; Reese → Gemini Kore; Tucker → Gemini Puck (match unverified); Sabrina → Gemini Aoede). Nothing is generated for that segment until Julie resolves the prompt; no voice is ever swapped silently. (Forever Pucked's cast — Violet (Gemini Zephyr) and Alex — are Gemini voices, so the FP phase is not expected to hit this path; the mechanism must still exist and be tested before arming, §7.)

### 6.5 Generation-capable client

Base: the accepted ui-pkg-3 client (commit `bf4e5ba2…`). The build wires the already-rendered generation controls to real commands:

- Per-chapter Generate, per-segment generate on "No audio yet" rows, and book-level Generate all submit **intent** — `SubmitJob` / `RequestRepair` to `POST /v2/commands` (the source-verified trigger path). The client submits intent and views status; it never drives the work (see server-owned continuation, below). Exact client identities (entry / SW / stylesheet successors, build and packaging markers) are TO BE PINNED IN BUILD, following the established versioned-successor pattern; shared modules and the store are changed only under the same preservation rules as UI1–UI3, and the frozen bridge stays byte-identical. UI3 and Shelf remain unchanged except for these reviewed generation-specific successor paths.
- **Standard-only, enforced at both layers.** Client: the confirm sheet's Standard | Batch switch renders Batch **disabled with the reason shown** ("Batch isn't enabled yet — it needs its own decision"), defaulting to Standard. Server: the coordinator refuses to grant, and the executor refuses to execute, any command carrying a batch lane — a crafted batch-lane command is rejected, not honoured (§7, Batch-disabled proofs). Defence in depth is deliberate: neither layer trusts the other.
- **Server-owned continuation — truly hands-off (Amendment A-1 — Rowan clarification 2; this redesigns the original §6.5).** The draft Rowan reviewed had the *client* chaining chapter submissions; that is not hands-off — a suspended or closed app would stop the book. The design is now: on intent submission, the **coordinator creates a durable per-job work plan** — the job's eligible occurrences (§5 eligible set, Ch 3 excluded) in reading order, each with its own state — **persisted in the coordinator's durable store**. The coordinator then **drives dispatch itself** against quota (100 attempts/day), the monthly cap, and the phase budget (§9): it grants and dispatches from the plan, records each occurrence's execution state (§4 state machine), and continues until the plan completes or a stop condition (quota exhausted for the day, cap, phase budget, unknown-billing halt) parks it. Continuation is **server-side and durable**: the plan resumes after a quota rollover (the next day's attempts) and after any worker or client restart, with no client contact required at any point after submission. **Per-occurrence idempotency**: dispatch is keyed to the plan entry and its execution record (§4) — an occurrence with a non-terminal or committed execution record is never dispatched again for the same execution, so restarts and rollovers produce zero duplicate dispatches and zero double synthesis. The designed "Keep going until today's quota runs out" toggle survives as the **scope of the intent**: with it on, the intent covers the book's full eligible set and the coordinator keeps going across days until the plan is done; with it off, the plan covers just the submitted chapter (or segment). Either way the driving is the coordinator's. The **client is intent-submitter + status viewer only**: it shows the plan's state in the same plain words as before (where it stopped, what remains, why it stopped) by reading coordinator state — display, never control. **The foreground-only alternative is explicitly NOT taken**: Julie's feature law is truly hands-off generation (confirmed Oct 20, 2026); a design that only works while the app is open would be a deviation requiring her explicit approval, which she has not given.
- Quota/cap display: the existing Settings quota counter (attempts today, spent of cap) becomes live data once generation exists; its rendering is unchanged.

### 6.6 Settings reconciliation — the geminiLane tension

`/v2/settings` currently reads `{"monthlyCap":50,"geminiLane":"batch","revision":0}`. A Standard-only case cannot arm against a settings record that names batch. Reconciliation, executed at the **arming step** (§8, step 5) — not in the halted deploy, so the sealed baseline stays sealed until the case is actually being armed:

- Before: `{"monthlyCap":50,"geminiLane":"batch","revision":0}`
- After: `{"monthlyCap":50,"geminiLane":"standard","revision":1}` — a single revisioned settings write changing exactly the lane; the cap is untouched.
- **The write is revision-checked (Amendment A-1 — Q2)**: it is a compare-and-swap conditioned on the current revision being **exactly 0**. If the revision read at arming time is anything other than 0, the arming sequence **stops** — a stale revision is never overwritten, and the discrepancy is reported, not repaired in passing.
- The write is verified by read-back (`/v2/settings` and `/v2/quota`) before the halt flip proceeds.
- Independent of settings, the executor's lane allowlist under this case is exactly `["standard"]` (representation TO BE PINNED IN BUILD): even a settings record that somehow named batch could not produce a batch execution while D6's shape is in force.

### 6.7 What the build does not change

No Shelf change (bridge frozen); no voice-mapping changes (mappings are recorded only, §6.4); no change to the v1 worker, its queue, or its paused delivery; no change to playback/sync behaviour or to any accepted client's data.

## 7. Test plan

All suites run on the exact final build trees (worker + client), complete runs, logs and exit codes pinned in the review artifact — the standing rule from UI1–UI3. NO real book text in any test: synthesis fixtures are synthetic strings; book-derived fixtures are structural only (IDs, counts, char lengths).

- **Existing batteries stay green**: the v2 worker suites and the client batteries (unit, cast census, Chromium proof, phone-width proof) against the new builds.
- **D10 failure-injection suite**: FI-1…FI-5 (§4), each asserting the full post-condition set (R2 state, binding state, ledger/attempt record, job report stage).
- **Flush-before-commit ordering proof**: an instrumented run asserting no binding/report commit timestamp precedes its verify pass, across success and injected-failure paths.
- **Quota/cap enforcement**: attempts counter increments per attempt (including failed and split attempts, per the ledger semantics in §4); granting stops at 100 attempts/day; granting stops at the $50 monthly cap; the coordinator's driver (§6.5) parks the plan cleanly at each limit and reports the stopping point; halt var at "1" ⇒ zero grants, zero drain, zero executions, at every layer independently.
- **Server-owned continuation (Amendment A-1 — clarification 2)**: (a) **restart mid-job** — kill the dispatch driver between dispatches; on restart the plan resumes with zero duplicate dispatches and zero re-synthesis of settled occurrences; (b) **quota rollover mid-job** — cross the day boundary mid-plan; continuation resumes the next day against the new day's quota, with no re-dispatch of settled occurrences and no loss of plan position; (c) **duplicate intent** — the same book intent submitted twice produces exactly one work plan (the second submission is recognised as the same intent, not a second job); (d) **client closed throughout** — an entire job runs to its stopping point with no client contact after the initial submission.
- **Crash-recovery scan**: FI-6 (§4) plus recovery of a plan whose driver stopped mid-dispatch — every non-terminal execution record is resumed from its recorded state or routed to reconciliation, none silently dropped.
- **Spend controls (Amendment A-1 — clarification 3, Q5)**: phase-budget enforcement — granting stops exactly at the §9 phase budget computed from known-cost settlements; an attempt with an **unknown billing outcome halts the phase** and blocks all further granting until reconciliation completes; reconciliation-before-retry — no occurrence with an unknown outcome is re-attempted while the outcome is unresolved; reserved grants are shown to be releasable without spend on plan cancellation.
- **Batch-disabled proofs**: (a) the client cannot select Batch (control disabled, state cannot be set programmatically through the UI layer); (b) a hand-crafted batch-lane command submitted directly to `/v2/commands` is rejected by the coordinator; (c) a batch-lane dispatch reaching the executor is refused. All three must pass.
- **Parked-job inertness**: with the full pipeline armed in the test environment and unrelated jobs executing, the parked Ch 3 job's state, grants, and occurrence dispositions are byte-identical before and after; the drain is shown to void/skip its dispatches; no code path in the build enumerates it as eligible; and specifically (§5, Q6) the job builder / work-plan enumeration is asserted to **never enumerate or dispatch any Ch 3 occurrence ID**, and no auto-resume path for the parked job exists.
- **Migrated-text proofs**: the §5 verification suite run as tests — completeness, ID set equality vs the frozen census, POV resolution, no-silent-skips enumeration, and the Ch 3 27-occurrence reconciliation report.
- **POLICY_BLOCK fixtures**: synthetic segments engineered (structurally) to trigger provider refusals in the stubbed adapter: single split, recursive multi-level split, recursion-floor terminal state reported by ID, and voice identity asserted constant across every split attempt (no substitution).
- **Repair-chain tests**: transient provider failure → server-owned retry with bounded attempts; terminal failure → clean terminal state, job continues with the next occurrence.
- **Removed-provider prompt test**: a fixture book whose cast voice is a removed-provider voice produces a mapping prompt and zero synthesis calls for its segments.
- **Smoke** (post-arming, attended — §8 step 6): (i) one synthetic Standard job end-to-end with byte verification and quota read-backs; (ii) one named real segment with Julie listening (§10).

5. **Arming** — separately authorized, in this exact order, each step verified by read-back before the next, and **each step carrying its own failure handling (Amendment A-1 — Q4)**: on any failure, the rollback/re-halt actions for that step are executed and read-back-verified — restore `GENERATION_HALT` to "1", pause the v2 queue's delivery, and **void any pending dispatches** so nothing leaks into execution later — leaving the system in the pre-arming halted state (or a named safe state stated at the time), never a silent half-armed state. The steps: (0) **production-data proofs** — the five §5 proofs run against deployment-bound data and pass, results filed (§5 arming precondition); failure here means arming does not start, nothing to roll back; (a) settings reconciliation (§6.6: revision-checked, 0 → 1, lane → standard, read-back verified; a stale revision stops the sequence untouched); (b) consumer attach (the v2 worker consumes the new queue; delivery still paused; the consumer is verified attached and correctly routed while nothing can flow); (c) halt flip (`GENERATION_HALT` "1" → "0", `/health` read-back shows generation no longer halted, `/v2/quota` still zeroed); (d) **queue delivery enabled LAST**.
6. **Smoke, then follow-on** — synthetic job, then the one named real segment (§10) with Julie listening. Only after smoke passes: a **follow-on proposal** for the unbound segments, Forever Pucked first (Julie's current listen) — and even there, the parked Ch 3 job resumes only on Julie's explicit word, and Ch 2's POLICY_BLOCK set goes through the §6.4 splitting path as designed. **Bulk approval requires the smoke's measured per-segment cost reported against the §9 estimate** (Amendment A-1 — clarification 3): the follow-on proposal carries the measured number, and the $13.50 phase budget (§9) governs the phase it approves.

**Re-halt path** (stated honestly, from the preflight): re-set `GENERATION_HALT` to "1", re-pause the v2 queue's delivery, and void pending dispatches (the same rollback set as the arming failure handling above). In-flight grants settle and cannot be un-spent; a re-halt stops new work, it does not refund attempts already made.
