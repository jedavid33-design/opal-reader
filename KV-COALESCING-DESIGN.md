# KV write coalescing — engineering design v2 (Rowan's corrections incorporated)

Branch: `kv-write-coalescing` (from main @ 1ad64946), local clone only.
Implementation begins only after tonight's iPad sync + Finding Home verification. Deployment requires separate approval after Rowan reviews the finished diff + measurements. Release identifiers (1.4.42 / 1.4.116 / GENERATION_RELEASE_ID) and all recovery/release protections stay intact.

Architecture (verified in code): `readGenerationStatus` reads **R2 first**, KV only as fallback; all mutation flows load through it. R2 is the authority; KV is a fallback mirror. `saveGenerationStatus` is restructured: **R2 put awaited first** (its failure throws — authoritative), KV mirror second in try/catch (failure logged, swallowed, and — per correction 1 — *not forgotten*).

## Correction 1 — mirror metadata tracks CONFIRMED writes only
- Stamps (`_kvState`, `_kvCompleted`, `_kvFlags`, `_kvMirroredAt`) describe the last **successfully mirrored** snapshot. They advance ONLY after a KV put resolves. A failed mirror leaves them stale, so eligibility persists.
- Eligibility rule: mirror when the current durable snapshot differs from the last confirmed one (critical transitions, correction 4), or progress thresholds are met (correction 4), or the status is terminal.
- **Catch-up without new transitions**: status-read paths (`readGenerationStatus` callers / the generation status endpoint) check the loaded R2 status against its confirmed stamps; if unsynced durable state exists, they schedule a background mirror attempt (waitUntil, non-blocking). A job that goes quiet after a failed mirror still converges to KV on the next poll — and the terminal save always attempts a mirror regardless.

## Correction 2 — counter windows stay Pacific-day + rolling 24h
The Gemini counters keep their existing semantics: **America/Los_Angeles calendar day** (matching Google's quota day — the app shows "reset 3:00 AM ET") plus a **rolling 24-hour** window, computed from ledger event timestamps with the worker's existing zone-offset helper. Cloudflare's UTC write-quota reset is a separate clock and is never used for usage reporting.

## Correction 3 — accounting matrix first; missing ledger events handled explicitly
Before touching the report, implementation produces an accounting matrix: for each path (Standard speech, Batch submit, Batch per-segment completion, Batch failure rows, provider errors, quota rejections) — what today's KV counters record vs what R2 ledger events exist. Where a path lacks a ledger event, the fix adds the **R2** ledger write at that point (R2 writes are monthly-bucketed; ~free at our scale) so the derived report is complete — or, if a gap is found that cannot be closed safely, the report marks that figure as partial instead of presenting it as exact. Tests pin the derived report against fixtures for every path in the matrix, including failure cases.

## Correction 4 — throttle rework: classify transitions, drop the 15s timer
The v1 "state changed → mirror" rule is wrong: queued↔generating flips happen per segment, and a 15-second timer fires on nearly every slow synthesis.
- **Critical — mirror immediately**: job staged/created; first activation; paused / paused_update; terminal (ready/partial/failed/cancelled); chain handoff (`continue_started`, next-job activation); error set; Batch operation assigned (`provider_request_id` — recovery-critical); adaptive split (children created).
- **Routine — never mirrored individually**: queued↔generating execution flips, per-segment completed ticks, cooldown/backoff bookkeeping.
- Routine progress reaches KV via: **volume catch-up** (≥25 segments completed since the last confirmed mirror), **terminal saves** (always), and the **read-path lazy catch-up** (correction 1). No wall-clock timer as a primary mechanism; benchmarks (below) decide whether a long floor (e.g., 5 min) earns its writes as a staleness bound.

## Additional requirement (Rowan) + concurrency correction (Julie/Rowan) — serialized mirror writer
A check-then-write version guard is NOT sufficient: two catch-ups can both read the same old version and then write in the wrong order (TOCTOU), and KV is eventually consistent with concurrent same-key writes overwriting each other (plus KV's own 1 write/sec/key limit). v2.1 therefore routes **every** write to a job's KV mirror — normal checkpoint mirrors and background catch-ups alike — through a single serialized mirror writer:

- **Per-job R2 lock via conditional operations.** Lock object `generation/mirror-lock/<jobId>.json` {owner token, acquired_at}. Acquire = R2 put with `onlyIf: { etagDoesNotMatch: "*" }` (fails/returns null if a lock exists — handle both semantics). Release = delete. Crash safety: a lock older than 20s is stealable via an etag-conditional replace (`onlyIf: { etagMatches: <observed> }`) — exactly one stealer wins. Bounded acquisition attempts (2, small jitter); losing is cheap — the mirror simply stays eligible for the next trigger. The R2 authoritative save NEVER waits on this lock; mirroring is best-effort after it.
- **Inside the lock, and only there, a mirror happens**: (1) claim the attempt — the 60s retry floor is checked and the attempt stamp recorded as part of acquiring (a poll that cannot acquire, or finds a fresh attempt stamp, schedules nothing — simultaneous polls cannot multiply attempts); (2) load the **latest R2 status fresh** (never a caller-held snapshot); (3) write that version — and only that version — to KV; (4) only after the KV put resolves, persist the confirmed stamps (correction 1: success is recorded after KV confirms, never before); (5) release.
- **Mirror metadata lives in its OWN R2 object** (`generation/mirror-meta/<jobId>.json` — attempt stamp + confirmed stamps), written only by the lock holder. It is never embedded in the status object, so confirming a mirror can never overwrite generation progress a saver wrote concurrently (Rowan's final safeguard 1). Throttle decisions live inside the writer, which loads meta + latest status under the lock. The status object itself gains at most an additive monotonic version field, written only by ordinary saves.
- **Fencing (Rowan's final safeguard 2)**: the lock object carries a monotonic epoch, incremented on every acquisition/steal. A writer captures its epoch and **re-validates ownership (owner token + epoch) immediately before the KV put and again before persisting stamps**; a failed validation aborts silently — its work is void. Releases are delete-only-if-still-mine, and a wrongful release is harmless because every write is preceded by the fence check. Tests must cover the exact scenario: holder stalls past the 20s expiry, a successor steals the lock and mirrors a newer version, the original resumes → it writes nothing, KV keeps the successor's record, stamps reflect the successor only. Plus: stamp-persistence racing a concurrent generation save → both the progress and the confirmation survive (separate objects, verified by interleaved mocks).
- **Version guard retained as defense-in-depth** (monotonic `_statusVersion`, bumped per save): inside the lock, if KV already holds a version ≥ the freshly loaded R2 version, skip the write. Under serialization this should never trigger; it exists to catch cross-path anomalies cheaply.
- Cost: a mirror becomes a few extra R2 operations (monthly-bucketed, 1M Class A/mo free) — negligible against the KV savings.
- **Tests (the four catch-up tests, hardened)**: mocks expose controllable async gates so completion order can be deliberately REVERSED — (a) KV down + 100 polls in a minute → exactly one attempt claim per job, no retry storm, reads unaffected; (b) two catch-ups + one checkpoint mirror racing with reversed completion order → final KV = newest R2 version, always; (c) lock holder "crashes" mid-section → lock expires, a stealer completes the mirror, stamps confirm exactly once; (d) KV recovers after failures → next eligible attempt mirrors the latest version and confirmed stamps advance; plus the stale-snapshot case: a writer holding an old in-memory status can no longer write it at all (the writer API takes only a jobId — snapshots are never accepted).

## Compatibility
Additive-only status fields (`_kv*`); payload/R2 schemas unchanged in shape; the client needs no changes (status endpoint already R2-first). Older in-flight jobs (pre-patch statuses without `_kv*` fields) are treated as "never mirrored" → first post-deploy save mirrors once and stamps thereafter.
