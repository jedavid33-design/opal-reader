- Surface: operator `GET /v2/d6-quota-reconcile`, page size

  offset validation.
- Complete only when: pages are pairwise disjoint; their
  union equals the reported totals for both arrays; the
  totals are identical on the first and last page; and

  (The flag's semantics are the ones CONFIRMED at gate (b):
  true only when one response holds both arrays whole.)
- Every page response is archived verbatim in the execution

THAT census, at THAT moment** — where `ok === true` means,
exactly as defined in the deployed source
(`quota-budget.mjs`): the drift list is empty **AND** no
current-day block exists.

**If the fresh census reads `ok: false` — for any reason —
the gate STOPS.** No flip, no unpause. The census is filed

it shows becomes a new decision item for Julie/Rowan. Two

- **Drift non-empty:** the books stopped agreeing with the

  proposal §10, restated at gate (b) §5.2) is absolute: an
  explained `ok: false` never satisfies re-arm.
- **`currentDayBlocked: true`:** a current-day block exists
  (an exception or drift entry touches the current PT day

  if the execution session fell inside a blocked interval,

### 5.0 The core invariant (PROVEN from source)

The only executor the production entry constructs is the D6
executor (`worker-entry-prod-d6.js`, `_execute`). Its
`handleMessage` runs, **before `claimGrant` is ever
called**, a strict pre-claim fence over persisted server
records (`d6-executor.mjs`):

1. **Strict plan resolution** (`resolvePlanForFence`): the
   plan identity comes from the `d6_plan_jobs` link
   cross-checked against the job's own `data_json` stamp —
   never from the message. Multiplicity, blank/corrupt
   records, disagreement, or any read fault all refuse
   (`plan_link_conflict` / `plan_state_check_failed` /
   `plan_link_mismatch`). A database fault never reads as
   "no plan" and never as dispatchable.
2. **Quarantine read** (strict, D8-1) against the resolved
   identity: a hold on the plan or the job refuses
   (`plan_quarantined`); a read failure refuses
   (`quarantine_check_failed`).
3. **Plan-state fence** (`planStateFenceRefusal`):
   `PLAN_STATES_REFUSED = {complete, partial, retired,
   halted_unknown}` — the exact complement of the driver's
   own selection — refuses `plan_not_dispatchable` **before
   claim**; any state outside the refused set *and* outside
   the recognized dispatchable set (`active` + the parked
   family) also refuses (`plan_state_check_failed`).

So a message can reach `claimGrant` only if its job
resolves to a plan in a dispatchable state with no hold —
or the job is genuinely plan-less. **Every D6 job in the
current inventory resolves to a plan in the REFUSED set**
(smoke → complete; stale Ch 2 → retired; fresh Ch 2 →
complete). The one plan-less job (Chapter 3) is covered
separately in Path A4: it holds no grant, so there is
nothing for `claimGrant` to claim.

Behind the fence — never reached by stale work — sit two
further layers, named so nobody mistakes them for the
proof: the **grant guard** (`grant-guards.mjs`, inside
`_issueGrant`: quarantine → phase halt → phase budget →
storage) for any grant *issuance*, and the now-**armed
quota guard** (`quota-budget.mjs`, written inside
`markDispatching`'s transaction — a call site reachable
only after a successful claim and a granted occurrence,
`d6-executor.mjs` per-occurrence dispatch path) for any
actual dispatch. The armed guard is a backstop for future
legitimate dispatch; §5's conclusions do not rest on it.

## 6. Execution sequence (for Julie's later, separate approval)

Mirrors Gate-7's A0–A6 order and gate (a)'s verification
discipline. Exactly **two mutations** (R3's flip upload,
R5's unpause PUT — plus R3's conditional observability
PATCH only if the stated trigger occurs). Each step is
read-back-verified; **any ambiguity at any step is a STOP**
— hold position, read only, no retry of a mutating step
without a fresh Julie go. **A Go covers one attempt.**

- **R0 — Preconditions + fresh census.** §3's twelve items,
  then §4's complete paginated census with
  `ok === true` at that moment, with a cf-api queue-pause
  read-back in the same pass. Any STOP condition ends the
  attempt here, before any mutation.
- **R1 — Julie's re-arm approval.** Her distinct decision
  on this reviewed proposal, recorded on the board BEFORE
  R2. (Rowan's review of this proposal authorizes nothing;
  this step is Julie's alone.)
- **R2 — Settings + routing: verify only, no write.**
  Settings rev 1 confirmed (lane `standard`, cap $50) —
  settings are **not** modified by re-arm. Queue
  attachments read back: sole consumer
  `opalreader-api-v2-prod`, sole producer the same script;
  bindings show the queue binding present and
  `GENERATION_HALT` still `"1"`; `/health` still
  `"halted"`. Precondition read-back immediately before
  R3: queue still PAUSED, halt still `"1"`, build still
  `945875bc…`.
- **R3 — R-flip: `GENERATION_HALT` `"1"` → `"0"`.**
  Mechanism, Gate-7's A4 exactly, with this gate's
  manifest: the flip envelope is assembled from the R0
  live download (28 parts, each verified byte-identical
  to the gate-(a) operative envelope parts-manifest) +
  the live upload metadata with **exactly one value
  changed**; with the value restored to `"1"` the
  assembled envelope must reproduce the live script's
  metadata exactly. PUT once. **Read-backs:** `/health`
  generation `"enabled"`, build unchanged; bindings
  name-keyed diff vs R0 = exactly one entry
  (`GENERATION_HALT`); script GET etag **expected
  UNCHANGED** (`d63b61c3…`) and downloaded parts
  re-verified byte-identical to the manifest (28/28).
  **Observability check (mandatory):** GET script-settings;
  if observability regressed to null/disabled, apply the
  conditional PATCH (multipart, `/settings` path,
  observability object only) and verify the etag is still
  unchanged afterward; if it survived (the outcome at
  every deploy in this chain), no PATCH is sent.
  **Ambiguous PUT response** (lost/timeout/5xx after the
  request may have landed): read back (health + bindings +
  etag) and STOP on any uncertainty — **never blind
  re-flip**; the state the read-back proves is the state
  the record states. **Rollback from here:** flip back to
  `"1"` (one metadata upload, same mechanism) — the queue
  is still paused, so the only machinery that can run in
  the interval is the alarm, which R4 watches.
- **R4 — Armed-idle verification, queue still paused.**
  Two parts: (i) an **immediate sweep** of the read set
  below; (ii) an **observation window of at least 12
  minutes** — longer than one full watchdog cycle
  (10 minutes), so at least one complete alarm pass
  (base alarm incl. outbox drain + `recover()` +
  `driveOnce()`) is guaranteed to occur inside the window
  — with the read set repeated at the end and compared
  value-by-value. (The 12-minute span follows gate (a)
  D0's three-sample precedent, tightened to a guaranteed
  alarm cycle; Gate-7's A5 was an immediate sweep only —
  the window is this gate's strengthening, adopted
  because §5.9 item 1 makes the watched window the
  operative proof for the schedule table.)
  **Read set (used identically at R4, R6, and any
  containment check):** `/health`; bindings (10 names +
  halt value); script etag; operator reconcile (`armed`,
  `ok`, day totals, exception count, drift count);
  client quota view; plan list + the three plan reads;
  the three job reads + Ch 3 fingerprint recomputed;
  conflicts (count **and** max id); phase figures;
  settings revision; watermarks (content + bindings
  snapshot heads). **Expected: zero movement on every
  value** vs R0/RC, except the two intended ones (halt
  `"0"`, `/health` `"enabled"`). Any other movement —
  a new attempt, a plan/job/grant state or revision
  change, a figure change, a **new conflict row**, a
  watermark move — = **STOP + containment (§7)**.
- **R5 — R-unpause, LAST.** cf-api PUT the queue with
  `queue_name` + `settings.delivery_paused: false`
  (the body is a positional argv JSON string — a `--data`
  flag is silently ignored by this CLI; standing lesson).
  **Independent read-back:** `delivery_paused == false`,
  sole consumer + retention (86,400 s) unchanged. A PUT
  response is never trusted without the read-back.
- **R6 — Post-unpause verification.** The R4 pattern
  repeated: immediate sweep + a ≥12-minute window (≥1

  prediction is refusal-with-ACK and **zero state
  movement**; a refusal leaves no trace in the read set

  containment trigger.

## 7. Containment and rollback

- **Re-halt and re-pause are ALWAYS permitted inside this
  gate without further approval.** Returning to the
  pre-state is the safe direction: on any anomaly at any
  point — a STOP condition, any read-set movement, any
  ambiguity that read-back cannot resolve — the executor
  re-pauses the queue (PUT, `delivery_paused: true`,
  read back) and re-halts (metadata flip back to `"1"`,
  read back), in that order (pause first: it stops new
  deliveries while the flip lands), then STOPs and files
  the record. Neither containment write needs a fresh go;
  both are recorded as their own read-back steps in the
  execution record.
- **This rollback is same-build.** It touches no code and
  no data: the flip is a one-value binding change on
  byte-identical parts, and the pause is a queue setting.
  The rollback floor (build `6a73d962…` + its data) is not
  implicated in either direction — no build rollback is
  part of this gate, and none would be permitted by it.
- **Ambiguity rule (Rowan's caution, carried from gate
  (b)):** a fault or lost response is never treated as
  proof that a mutation did or didn't land. Read-back
  establishes the state; uncertainty is a STOP, with
  containment (above) as the only writes permitted while
  uncertain — and only because their direction is safe
  regardless of which way the ambiguous write landed
  (re-halting an already-halted system and re-pausing an
  already-paused queue are both no-ops if already there;
  each is still read back).
- **One attempt:** if the gate is contained or STOPped,
  a second attempt requires Julie's fresh authorization.
  The execution record states exactly where it stopped
  and the state the system was left in.

purpose and its risk, stated without softening:

- From the moment R3 lands, the only things standing
  between a dispatchable intent and a provider call are
  the live controls: the **armed quota guard** (fresh
  `ok: true` census at §4, per-dispatch ledger, 100/day

  does not and cannot prove anything about *future*

  times.** §7's containment is pre-authorized inside the
  gate precisely so a surprise costs minutes, not a

  authorizes generation. It can also persist indefinitely

  UI's buttons become live. That is the intended end
