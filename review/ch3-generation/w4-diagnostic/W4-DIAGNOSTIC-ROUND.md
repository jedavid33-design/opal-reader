## 1. The mechanism in brief (live build, source-cited)

- The coordinator keeps a `schedule` table. `_armAlarm()` (coordinator.mjs:2790) sets the platform alarm to the minimum `due_at` over pending rows, or `now + WATCHDOG_PERIOD_MS` (600,000 ms = 10 min, :133) when none is pending.
- `coordinator.alarm()` processes due rows (grant leases, retries, the watchdog) and, in its `finally`, ensures a pending watchdog row exists and calls `_armAlarm()` **unconditionally** (containment arm gate aside; containment has read NORMAL at every observation in every silence below — suppression never engaged). Each delivered pass therefore arms the next. `service.driveOnce()` has exactly one caller: this alarm path.
- The **recorder** (entry subclass, `worker-entry-prod-d6.js`: table `d6_drive_passes` :434, health object `d6DrivePassRecorderHealth` :455, recording at :1888) runs last on the alarm path and writes one row per pass: stage, `driveInvoked`, allowlisted outcomes, error name/message if thrown, and `armedAfter` = the post-pass `getAlarm()` value; it prunes to the newest 288 rows, and **rethrows any original error unchanged** — so a pass that throws still records its row, and each of the platform's retries (documented: up to 6, exponential backoff) is another recorded pass.
- `wake()` (:3200) ensures a watchdog row, then calls `_armAlarmIfEarlier(armMemo)`. Its only callers are the operation paths: `handleCommand`, `requestGrant`, `handleReport`. A **replayed** command returns its stored receipt *before* `wake()`. **No GET/read path calls `wake()`** — the `drive=1` diagnostics read is documented in its own header as read-only ("no wake, no command, and no mutation is reachable from here").
- `_armAlarmIfEarlier` (:3220), the R5a form as deployed since Grant 1 (2026-11-02, build `fdb02395…`, carried unchanged into the live build), registers `setAlarm(due)` only when: `armed` is null/undefined, **or `armed <= now − ALARM_STALE_THRESHOLD_MS`** (3,600,000 ms = 1 h, :144 — the past-due disjunct), **or `due < armed`**; with a per-operation arm memo and the containment v3 race recheck. It never moves an alarm later and never re-sets an equal value on the `due < armed` branch.

The consequence that governs everything below: **the only unconditional re-arm in the system lives inside the alarm handler itself, and the only other registration path (R5a's) runs exclusively inside operations that have not occurred since the current silence began.**

## 3. What the evidence narrows — and the caveat it cannot remove

- **Not a handler-failure story, on the recorder's own design.** A pass that is invoked and throws is recorded, and its retries are recorded. Across S-1 and S-2 there are **zero** rows after the last pass and **zero** recording failures at every observation — over days of hourly and 6-hourly reads. The space is narrowed to: the due alarm was **never invoked**, or the invocation failed **before any user code ran**.
- **The preserved caveat (assessment §5, §10 item 10), carried at full strength:** a pass whose SQL record **and** KV health write both fail leaves no row, so absent rows narrow but do not eliminate the space of unrecorded passes. Nothing in this package claims past that caveat.
- **Not containment.** The arm gates read NORMAL on both surfaces at every observation in S-1 and S-2; suppression was never engaged. A verified chain stop would additionally have deleted the registration; the registration *stands*, which is itself inconsistent with a containment stop.
- **Not a deploy.** The one observed deploy-over-pending-alarm instance (S-0) neither dropped, retimestamped, nor revived the value; S-2 contains no code deploy at all after the chain's last pass (the 01:25:44Z S1 deploy preceded a healthy chain; the 04:50:45Z flip was metadata-only, etag unchanged, and post-dates the cessation).
- **The platform documentation boundary (assessment §3.2) is unchanged:** post-retry-exhaustion `getAlarm()` semantics, catch-up delivery for overdue alarms, and any reconciliation/revival mechanism for a never-invoked alarm are all **UNSPECIFIED**. "No self-healing mechanism was identified in the reviewed documentation" — never that none exists. Platform telemetry that could discriminate further (Workers Logs) is not readable on our credential (the telemetry query route 403s), and no step in this round proposes changing that.

## 4. Hypothesis register

- **H-1 — the fault ate the delivery.** The due invocation (and any retries) failed at the platform level during a 1101 fault, before the handler ran; once the fault cleared, nothing re-registered because nothing wakes the coordinator. *Supports:* S-2's tight bracket (due time inside a sustained, verified fault); the design fact that post-fault the chain has no self-recovery path (§1). *Against/limits:* S-1's onset is unbracketed; S-0's fault context is a named gap (G-1). *Status:* leading for S-2; unproven as the general cause.
- **H-2 — clear-weather delivery loss / read-registration divergence.** The platform holds (or merely reports) a registration it does not deliver, with no fault involved — the assessment's B1 delivery-side family ("the platform holds an armed value it reports faithfully but does not deliver — or the registration was consumed in the fault while `getAlarm()` continues to report the stale timestamp"). *Status:* preserved; becomes primary if G-1 or a future bracket shows a silence beginning in clear weather.
- **H-3 — invocation failed pre-handler (observability limit).** Observationally identical to H-1 on every surface we can read; listed so the register marks the boundary of what our evidence can ever separate without platform telemetry. *Status:* preserved as a limit, not ranked.
- **H-4 — the recovery shape is the defect (cause-independent).** Whatever loses a delivery, the system's recovery geometry guarantees permanence: the unconditional re-arm lives only inside the alarm handler; R5a's cure is wake-gated; reads are deliberately inert; a DO with no traffic runs no code at all. A single lost delivery is therefore fatal to the chain until an unrelated command happens by — **proven at source strength (§1) and observed three times.** *Status:* proposed as the round's primary frame: H-1…H-3 ask why deliveries are lost; H-4 is why a loss never heals, and it is the only one of the four a design change can actually address.
