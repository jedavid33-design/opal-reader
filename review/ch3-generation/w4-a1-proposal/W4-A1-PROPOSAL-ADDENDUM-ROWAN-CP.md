## How each correction is resolved

- **A1-C1 — discharged by the documented input gate, with the residual withdrawn.** Investigation as directed. The Alarms documentation states alarm operations are Storage API operations that "follow the same rules as other storage operations"; the SQLite storage reference (the deployed coordinator's backend — `this.sql = state.storage.sql`, coordinator.mjs:688) lists the Alarms API among its method families, each "implicitly wrapped inside a transaction… atomic and isolated." The Rules of Durable Objects (updated 2026-11-05) document that input gates block new events during storage operations — the worked example is a get-then-put across awaits, annotated safe *because* of the gate — and that the protection ends only at non-storage I/O. The evaluation's sequence from entry to act contains exactly two awaits, both storage operations (`getAlarm`, `setAlarm` initiation); a **new construction rule** binds the implementation to keep it that way (statically scanned, T-35). Under the documented semantics no event — command, report, alarm delivery, containment transition — can be delivered inside that window, so a superseded observation cannot occur at the moment of the act, independently of due selection (your second point is accepted on its own terms: nothing rests on due ≤ stale). Coverage is tabulated for every registration site (`_armAlarm` :2816; `_armAlarmIfEarlier` :3241/:3267) and both deletion sites (stop :3003, verify :3132) — none mixes a non-storage await into its sequence. The deployed configuration is compatibility_date `2026-08-29` + `nodejs_compat`; gating is documented as unconditional runtime behavior, not a flag or date behavior. `blockConcurrencyWhile()` was considered and not adopted (documented for initialization/migrations; it would also block the alarm event itself). Strength is stated honestly: this is a *documentary* demonstration; the harness still models interleavings the documentation excludes, so the boundary stretch is retained as construction — and the revision-fence fallback is sketched in §1.4, fully determined, so you can mandate it without another design round if you judge the bridge insufficient. Notably, with the demonstration in place, **no existing function needs modification after all** — your release of the additive-only constraint is acknowledged and unspent.
- **A1-C2 — enforcement moved into the boundary; derivation is the only authority.** The sequence is restated in three phases; the strike derivation and the intent insertion (the reservation) now happen **inside Phase B**, the synchronous stretch, before the watchdog ensure and the act. Eligibility is derived only there, from the events table — a second evaluation's Phase B runs wholly before or after, and counts every prior reservation, so the counterexample's fourth registration cannot occur in any interleaving (T-18 rewritten to prevention and harness-testable again, since Phase B's synchrony holds under any scheduler).
