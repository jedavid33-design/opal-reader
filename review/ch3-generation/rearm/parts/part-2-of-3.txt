### 5.1 The core invariant (carried from gate (c) §5.0, PROVEN there from source)

The only executor the production entry constructs is the
D6 executor. Its `handleMessage` runs, **before
`claimGrant` is ever called**, a strict pre-claim fence
over persisted server records: (1) strict plan resolution
(plan identity from the `d6_plan_jobs` link cross-checked
against the job's `data_json` stamp — never from the
message; multiplicity, blank/corrupt records, disagreement,
or any read fault all refuse); (2) a strict quarantine
read against the resolved identity (a hold refuses; a read
failure refuses); (3) the plan-state fence —
`PLAN_STATES_REFUSED = {complete, partial, retired,
halted_unknown}` refuses `plan_not_dispatchable` **before
claim**; any state outside both the refused and the
recognized dispatchable sets also refuses. **Every D6 job
in the current inventory resolves to a plan in the REFUSED
set** (smoke → complete; stale Ch 2 → retired; fresh Ch 2
→ complete). The one plan-less job (Chapter 3) holds no
grant, so there is nothing for `claimGrant` to claim.
Behind the fence — never reached by stale work — sit the
grant guard (inside grant issuance) and the armed quota
guard (written inside the dispatch transaction, reachable
only after a successful claim). The armed guard is a
backstop for future legitimate dispatch; §5's conclusions
do not rest on it.

### 5.2 Paths A–G (carried conclusions, gate (c) §5)

- **A — a queue message naming stale work is delivered.**
  Stale Ch 2 job → `retired` refusal before claim; smoke
  job → `complete` refusal; fresh Ch 2 job → `complete`
  refusal on plan state whatever its residue reads. Each
  refusal returns HTTP 200, so the queue handler **ACKs —
  the message is consumed permanently**, never retried
  into the fence. Chapter 3 job: plan-less, grants [] —
  nothing to claim; a fabricated grant id gets
  `unknown_grant`; the per-occurrence loop skips every
  non-`granted` row regardless (Ch 3's rows are
  `ready`/`pending`).
- **B — the coordinator alarm: driver selection.**
  `driveOnce` selects plans with `state NOT IN
  ('complete', 'partial', 'retired', 'halted_unknown')`.
  **All three current plans are in the excluded set** —
  the driver iterates zero plans on every 10-minute alarm
  pass. No plan → no re-advance, no new grant, no state
  transition; `retired` and `complete` are terminal in the
  driver.
- **C — the coordinator alarm: recovery.** `recover()`

  no-op on this inventory. It has run on every alarm cycle
  throughout the halted era — including the entire
  halted + paused period since the Ch 3 deploy — with

  wiring change the flip makes).** While halted,
  `sendGrant` is not wired, so unsent `dispatch` outbox

  retries).** `watchdog` re-arms the chain + drains the

### 5.4 The fuse inventory + the corrected window law (carried verbatim in substance from gate (c) §5.9, as corrected by Rowan 6547455532 and accepted in pin `73aa1220…`)

1. **The `schedule` table cannot be enumerated on any live
   read surface.** Pending-row existence is therefore
   bounded, not listed: creation call sites + fuse lengths
   + successively byte-identical inventories across eras
   (gate-(a) D0, gate-(b) B0, gate-(c) R0, the Ch 3
   deploy's pre/closing captures) + Path E's per-kind
   worst cases. The fuse lengths, from the deployed source
   (`worker/coordinator.mjs`, unchanged in this build —
   the part is among the 24 identical): `LEASE_MS` =
   15 min (lease rows are scheduled at `now + LEASE_MS` —
   at issuance and at handoff anchors); the poison-row
   failure backoff is `min(30000 * 2 ** attempts,
   900000)` — a per-retry cap of 15 min,
   `SCHEDULE_MAX_ATTEMPTS` = 8; `WATCHDOG_PERIOD_MS` =
   10 min; `retry_grant` fuses are 30 s / 60 s
   frozen-deferred; `handoff_check` starts at 30 s, defers
   60 s frozen, and backs off `30000 * 2 ** (tries - 1)`
   for tries ≤ 5 — at most 8 min; the frozen lease
   deferral tolls at 60 s. **The longest single fuse on
   any stale-work-relevant row kind is therefore 15 min.**
   §4's windows are sized against that figure — longest
   fuse (15 min) + one full watchdog cycle (10 min) +
   margin = **≥30 min** on both sides of the unpause —
   and are **bounded observation, not exhaustive schedule
   proof**: every creation event for stale work lies in
   October and every fuse is ≤15 min, so any legacy
   pending row's due time is long past and it fires at the
   first alarm pass inside a window; a row created during
   a window with the longest fuse likewise falls due and
   fires inside it; and any movement either causes is a
   containment trigger. **One case the windows do not
   close, stated plainly:** a row that *throws* when
   processed re-enters the failure backoff — per-retry
   ≤15 min, up to 8 attempts, a cumulative worst case of
   ≈60 min before it parks `dead` — so a mid-backoff row
   can outlive a window. It is covered not by the window
   but by §5's per-kind source-path fences, which refuse
   or no-op **whenever** such a row fires, and by the
   movement triggers: its only reachable visible end
   states are the fenced handlings above or a new
   `schedule_dead` conflict row, each a STOP + containment
   event whenever it occurs, inside or after a window.
   The windows corroborate; the fences are the
   load-bearing proof. This is a monitored condition, not
   an assumed negative. *(The superseded gate-(c) first
   draft's ≥12-minute window claim is NOT carried anywhere
   in this proposal; Rowan's correction stands.)*
2. **Fresh Ch 2 job/grant terminal states** are named R0
   reads (§3 item 9), with the `handoff_uncertain` case
   escalated to an R0 STOP (Path E). The plan-state proof
   (Paths A/B) does not depend on the outcome.
3. **Queue backlog depth is unobservable** (unchanged
   since Gate-7). Bounded by retention + single-dispatch
   provenance; covered by Path A on delivery.

### 5.5 The delta surfaces — what build `63d7260e…` adds, assessed fresh

1. **The four operator routes.** They exist in the entry

2. **The parked job's release path, in code.** Build
