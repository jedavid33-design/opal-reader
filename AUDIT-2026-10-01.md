# Opal Reader — full generation/playback audit, 2026-10-01

**Scope:** every way a chapter can end up half-built, stuck, or unplayable — and what production actually looks like right now.
**Code audited:** frontend `app-181.js` (v1.4.43, current); worker behavior verified against the **deployed** worker v1.4.12 via its observable API + production data (see §4 — the repo's `cloudflare-worker.js` is stale, v1.4.8).
**Production audited read-only:** KV namespace `0e6fc5f440684b628db4b1e3b16486b1` (23 `generation:*` statuses, `library:index`, 3 `book:*` records), R2 bucket `opalreader-storage` (audio objects, job payloads). Nothing written, nothing deleted.

**Bottom line:** the machinery is fundamentally sound — strict completion checks, deterministic cache keys, self-healing on missing audio, no stuck queue jobs in production. The real hazards are (1) a lost queue message leaves a chapter showing "generating" forever with no recovery path, (2) queue redelivery can double-spend Gemini quota (visibility timeout is the 30s default), and (3) status application trusts array position where it should verify identity. Chapter-by-chapter production results in §3.

## Part A — static audit findings, ranked

### MAJOR

**A1. Lost queue message → chapter stuck at "queued"/"generating" forever, no UI recovery.**
`qe()` makes `job_id` a deterministic SHA-256 of book+chapter+cache_keys, and the worker's POST handler returns the existing status (`if (existing && ["queued","generating","ready"].includes(existing.state)) return existing`) *without re-enqueueing*. So if the queue message is ever lost after the status is saved (worker crash between KV put and `queue.send`, or a message expiring), tapping Generate just returns the same stuck status. The frontend polls it every 2.5s forever (`Ye`/`ct`), showing a spinner with no error and no way out — the KV record only expires after 14 days.
*Fix:* re-enqueue on POST when the existing status is `queued`/`generating` but `updated_at` is older than a few minutes (stale-heartbeat resume), or add a worker-side watchdog. Frontend: after N consecutive poll failures, mark the local generation failed with "tap Generate to restart."

**A2. Queue redelivery → same segment synthesized twice → double quota spend.**
`processGenerationJob` has no idempotency guard: two concurrent deliveries of one segment both pass the `status.state === "ready"` early-return (neither has finished), both see `hasCachedAudio() === false`, both call Gemini. The queue `opalreader-generation` has **no custom visibility timeout, so it's the 30s default**; any Gemini TTS call slower than 30s triggers a redelivery while the first attempt is still running. Both write the same R2 key (storage is idempotent, last-wins) so playback is fine — but each duplicate burns one of the 100/day Gemini requests and real money. Same on worker crash mid-synthesis: redelivery re-synthesizes from scratch.
*Fix:* raise visibility timeout to ~120s; add a cheap KV lease (`processing:<job_id>:<index>`, short TTL) checked before synthesizing; re-check `hasCachedAudio()` immediately before the provider call.

**A3. R2 write failure discards a successful synthesis → retry pays twice.**
If the provider returns audio but the R2 `put` fails, `synthesizeAudio` throws, the segment is marked failed, and the retry re-runs the *entire* provider call. The paid audio is thrown away. (Related: `readGenerationPayload` uses a raw R2 `.get` with no `retryStorageRead` — a transient read blip on the job payload fails the whole job.)
*Fix:* on R2-write failure, retry the *write* (with backoff) before failing the segment; never re-synthesize audio you already paid for.

**A4. `or()` applies ready audioKeys by array index with no identity check.**
`or(e, status)` does `e.segments[u].audioKey = status.segments[u].cache_key` for every ready segment. The completion check `sr()` correctly requires count match (`completed === total === segments.length`), but the *application* happens unconditionally first. Trigger: Julie splits a segment (review dialog → "split" — user-triggerable, nulls audioKeys and changes the count) while that chapter's job is still in flight. Segments after the split point then receive the wrong chapters' audio by shifted index — the chapter can look partially playable with *wrong* audio, which no later check detects (keys are valid, just misaligned).
*Fix:* in `or()`, only apply when `status.total === e.segments.length`; better, match by `cache_key` instead of position.

**A5. Poll failures are silent → "generating" spinner forever.**
`Ye()` wraps each chapter's status fetch in try/catch that only `console.warn`s. If the status 404s (KV TTL expired after 14 days, or the job never existed server-side), the chapter keeps its local `queued`/`generating` state indefinitely with zero user feedback.
*Fix:* count consecutive poll failures per chapter; on 404 or N failures, set local generation state to `failed` with an actionable message ("Generation expired — tap Generate to restart").

### MINOR

**A6. Network failure during playback → silent stall (unhandled rejection).**
`Ot()` does `await Bt(s)`; `Bt` → `At()` *throws* on network errors (only 404/503 return null). The throw propagates out of `Ot`/`Me` as an unhandled promise rejection — playback just never starts, no alert. (Genuine 404 correctly nulls the audioKey and tells her to regenerate — that path is good self-healing.)
*Fix:* try/catch around `Bt()` in `Ot()`; on throw, alert "Couldn't reach the audio — check your connection" without touching audioKey.

**A7. Regenerate dialog over-promises.**
`Wr()` says "The existing audio stays in place until the replacement is fully ready" — but `or()` applies each replacement segment's audioKey the moment *that segment* is ready, so old audio swaps out progressively, not all-at-once. Also `Wr` doesn't cancel a concurrent original generation; both jobs write to the same segments (last-writer-wins, both valid — harmless, but worth knowing).

**A8. `Mr()` doesn't pre-check that the voice's provider is configured.**
`regenerateOneSegment` checks `a.providers[s.provider]` up front; chapter Generate doesn't — a misconfigured provider fails the whole queue job server-side instead of alerting immediately.

**A9. `qe()` runs twice per Generate** (once for the cost estimate, once for the real payload). Harmless (SHA-256 is cheap), just wasteful.

**A10. Splitting a segment orphans the original's audio in R2.**
Split nulls the affected audioKeys (correct), and unchanged segments are skipped on regen via `hasCachedAudio` (correct — no re-spend). But the pre-split segment's audio object stays in R2 forever, unreachable. Contributes to slow storage growth (see §3).

**A11. PROCESS: repo worker source is stale.**
`cloudflare-worker.js` in this repo is APP_VERSION **1.4.8**; the deployed worker is **v1.4.12**. None of the v1.4.9–v1.4.12 fixes (finishReason reporting, fail-fast noRetry, R2 read retries) exist in the repo. The repo is not the source of truth for the worker — future fixes can't be developed or reviewed from it. Recommend committing the deployed source.

### Checked and cleared (no issue)
- `sr()` completion gate is strict (state=ready AND completed=total=segment count AND every segment ready with cache_key) — a chapter can't be marked complete with holes.
- `ir()` (playable check) requires every segment to have an audioKey; `Ot()` nulls the key on R2-404 so a chapter with missing audio stops claiming to be playable.
- `Ye`/`ct` polling is visibility-aware (2.5s while visible, pauses when hidden, resumes on visible) — background stall covered.
- Poll cost accounting carries `recordedCost` forward per job — no double-counting of spend across polls.
- Composite playback: skipped for >10 segments; 404/422/413 falls back to segment playback.
- Re-import creates a *new* book id, so it can't misalign an in-flight job's indices. Deterministic `job_id`/`cache_key` mean re-imported or re-voiced chapters reuse R2 audio via `hasCachedAudio` instead of re-spending.
- Single-segment regen (`regenerateOneSegment`) fails fast on content-filter refusals (only 429/network retried) and recomputes chapter readiness honestly.
